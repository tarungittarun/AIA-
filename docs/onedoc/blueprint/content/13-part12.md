# Chapter 29 — The operating loop

## 29.1 Reading order (first 30 minutes)

1. This Part XII (10 min): the loop, the ledgers, the blockage rules.
2. Part I (5 min): promises, constraints, out-of-scope — the constitution.
3. Part X §21–§22 (5 min): verdict vocabulary, gates, CI budgets.
4. Part V §13 (5 min): the ten laws.
5. Skim Part II catalogue + Appendix D gate DoDs (5 min): what "done" means.

Then work gate-by-gate. Do not write code for a chapter you have not read; do not open a gate whose predecessor is open.

## 29.2 The ledgers (append-only, always)

- **Decisions** — `docs/onedoc/plan/decisions.md`, format `D-nnn / date / context / decision / consequences`. Every non-trivial choice (dependency added, schema changed, fidelity altered, budget traded) gets one entry before the code lands. Entries are never edited; a reversed decision gets a new entry referencing the old.
- **Sessions** — `docs/onedoc/plan/sessions.md`, format `S-nnn / date / goal / done / failed / next`. One block per working session, appended at session end even when the goal failed — especially then.
- **Gates** — `reports/onedoc/gates/G<k>.md`: one report per gate, DoD checklist with evidence links, verdict, open items.

## 29.3 The task graph

`docs/onedoc/plan/task-graph.yaml` seeds every task with id, gate, depends-on, DoD, and case bindings. The agent expands each gate's slice just-in-time (details of G4+ are deliberately unplanned at G1 — plan-depth is a liability at 5 gates' distance), keeps statuses honest (`todo/doing/blocked/done` with evidence links), and never marks done without its DoD met.

## 29.4 Ambiguity and blockage

1. Blueprint first: §1.5 defaults resolve most ambiguity; record the chosen default as D-nnn.
2. Platform convention next (Material 3, Android patterns).
3. Still ambiguous and consequential (user-visible, irreversible, budget-affecting): choose the smallest reversible option, log it as D-nnn with the reopen condition, and surface it in the next gate report under "Decisions awaiting owner review".
4. Hard blockage (tool missing, quota exhausted, environment broken): mark tasks `blocked` with reason, close what remains closeable, and write the blockage into the gate report — a stalled agent that reports precisely is doing its job; a stalled agent that invents scope is not.

## 29.5 Quality self-checklist (every PR)

Laws touched? → property tests updated. UI touched? → registry row + DQ checklist. Format touched? → golden round-trip. Schema touched? → migration + D-nnn. Perf touched? → budget re-measured. Catalogue touched? → `traceability.py --check --strict` green. If none apply, say so in the PR body — the checklist's purpose is to force the question.

# Chapter 30 — Open risks and the v1.1 shelf

## 30.1 Watchlist

| Risk | Signal to watch | Pre-agreed response |
|---|---|---|
| IME diversity breaks composition invariants | fuzzer red on any keyboard | freeze features, IME-only gate (§15.3) until green |
| LLM RAM envelope too tight on real Tier A | gen latency > 2× budget on API 36 AVD | demote assistant to rung 4 default, keep rung 3 for ≥ 12 GB devices (D-nnn) |
| Pagination parity drift (guide vs PDF) | TC-STRUCT-004 off-by->1 | single-metrics-engine audit; freeze font fallback changes |
| APK size creep | PR size delta > +0.5 MB | shrink pass before any feature merge |
| Figma drift | DQ-3 failures | registry re-sync task; drift report to owner |
| OCR accuracy below fixture bar | TC-AI-001 accuracy < 95% on fixture set | pack version bump; ladder gains "confirm each page" rung |

## 30.2 The v1.1 shelf (recorded, not scheduled)

Markdown input shortcuts while typing · footnotes endnote mode · custom template import (.odoc as template) · neural TTS pack · additional OCR language packs (hi, mr) · writer-flavor distribution. Items graduate to the plan only by owner decision; the agent builds them only after a D-nnn says so.

## 29.6 Communication artifacts (what the owner sees, when)

| Cadence | Artifact | Location |
|---|---|---|
| every session end | session log block (S-nnn) | docs/onedoc/plan/sessions.md |
| every decision | ledger entry (D-nnn) | docs/onedoc/plan/decisions.md |
| every PR | checklist-filled description | GitHub |
| every gate | gate report + evidence links | reports/onedoc/gates/G<k>.md |
| every RC | evidence PDF + tracker diff | reports/ |
| release | release notes + handoff note + provenance bundle | GitHub Release + releases/<ver>/ |

Tone rule for all artifacts: facts with links, no adjectives ("green", "3 FAILs closed by OD-012" not "great progress"). The owner should be able to reconstruct the program's entire history from artifacts alone, without asking a single question.

## 29.7 The agent's daily loop (operating cadence)

1. **Morning:** read nightly results; red nightly = today's first task (§N.6). Check BLOCKED register for retry candidates with new tooling.
2. **Work block:** pull the top task from the graph whose dependencies are done; expand its slice just-in-time; write the test/procedure first where the type demands it (laws, formats, security).
3. **PR cadence:** small PRs (≤ 400 changed lines excluding generated), checklist-filled (§29.5), merged only green.
4. **Ledgers:** D-nnn at decision time (not end of day); S-nnn block at session end with the failed/next lines honest.
5. **Gate approach:** when a gate's DoD is within reach, freeze new scope, close evidence gaps first (evidence debt is the only debt that compounds).
6. **End of day:** task-graph statuses true; gate reports touched if evidence moved; nothing "done" without its DoD.

## 30.4 Post-v1.0 maintenance protocol

Between releases the program runs in "lighthouse mode": nightly pipelines keep running (emulator matrix + properties + fuzzer), dependency audit weekly (deny-list + lockfile refresh review), and every D-nnn-marked shelf item (§30.2) waits for an owner decision. A maintenance cycle re-runs the release checklist on any rebuilt artifact — no rebuild ships without evidence, including "just a dependency bump" (the SBOM and provenance regenerate; §28.2).

## 29.8 Asking the owner (the template for genuine blockers)

When §29.4's ladder exhausts and the matter is truly the owner's (keystore, Figma access, scope change, quota change), the agent posts ONE structured request, in the gate report under "Decisions awaiting owner review":

```
ASK-<n> (date, gate)
Need: <one sentence>
Options: A) <x — cost/risk> B) <y — cost/risk> C) do-nothing <consequence>
Recommendation: <option + why>
Workaround until answered: <what proceeds without this>
```

No repeated pings; the ask lives in the report until answered (answer becomes a D-nnn). This keeps autonomy honest: the agent never blocks silently and never nags.

## 29.9 What the agent must never do (the short list)

1. Never add a network permission, account, ad SDK, or telemetry — §1.3/§1.4 make such tasks invalid, not negotiable.
2. Never edit history: no rebase/force-push on program branches, no edits to closed gate reports, ledger rows, or the predecessor program's artifacts.
3. Never mark a gate/task done without its DoD evidence link.
4. Never write a user-visible string in code (keys only), a color literal in UI (tokens only), or an error ad hoc (taxonomy only).
5. Never let AI output enter a document without preview + explicit insert + pre-edit version (Law L10).
6. Never report a blocked gesture as FAIL — or as PASS (§21.2 cuts both ways).
7. Never claim calculator-grade parity claims about formats: state the fidelity level achieved (§18.2).
8. Never bundle a model into the APK (C5) or fetch anything at runtime (C1).
9. Never ship a rebuild without re-running the gates on that exact artifact (§28.6).
10. Never "temporarily" disable a test to go green — quarantine with a defect id is the only honest path (§24.3).

## 30.5 A note to the builder

If you are the agent holding this document: everything you need is here on purpose. The laws tell you what must never break; the catalogues tell you what must exist; the gates tell you when to stop and prove; the ledgers tell you how to remember. Build small, prove constantly, write everything down — and the owner will never need to trust you, because they can always verify you. That is the whole method.
