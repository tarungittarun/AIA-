@PART: PART X — QUALITY METHODOLOGY AND GATES
@PARTDESC: The gate plan G0–G8 with DoDs, the CI architecture and its budgets, the emulator matrix, the direct-APK QA pipeline that produces the evidence PDF, and the defect system. The rules here are inherited from a prior program's hard-won lessons and are not negotiable.

# Chapter 21 — Quality methodology

## 21.1 The principle: prove on the artifact

Source-level tests (JVM, Robolectric, instrumentation) are development aids. The **proof** that the owner holds is always the same shape: a GitHub Actions run that built the **release APK**, installed it on emulators, drove the real UI, and produced an evidence PDF whose every PASS/FAIL/BLOCKED row cites a case id and carries screenshot provenance. A green publisher job is *not* a passing QA result — QA shards decide the verdict, and their failures must surface as FAIL in the report even when publishers succeed (`if: always()`).

## 21.2 Verdict vocabulary (normative)

| Verdict | Meaning | May be counted as |
|---|---|---|
| PASS | the asserted behavior was exercised and held | PASS |
| FAIL | the asserted behavior was exercised and broken | FAIL — a defect row is opened |
| BLOCKED | the environment (emulator, accessibility tree, input synthesis) prevented a fair assertion | neither — re-triaged every cycle |

BLOCKED doctrine (inherited, hard rule): a blocked gesture — e.g. a stationary hold-then-drag that `adb input` cannot reproduce — is never evidence of a product defect and never evidence of health. It is logged with reason + environment fingerprint and re-tried in later cycles with new tooling. BLOCKED counts never silently shrink without a defect id or a tooling-change decision (D-nnn).

## 21.3 The test pyramid, budgeted

## 21.4 Performance budgets (enforced, not aspirational)

| Metric | Budget | Measured by |
|---|---|---|
| Cold start → first interaction, 200 docs, Tier B | < 1.2 s | TC-PERF-001 macrobenchmark + APK run |
| Typing latency P95, 10k-word doc | < 50 ms | TC-PERF-002 frame metrics |
| Full-text search, 200 docs / 1 MB | < 300 ms | TC-SRCH-001 |

Regression = budget exceeded on the emulator matrix → S2 defect. Optimizations ship with before/after numbers in the decision ledger.

# Chapter 22 — CI architecture

## 22.1 Budgets (C8, hard)

Maximum **3 parallel runners**, maximum **30 jobs per pipeline run**. Workflows achieve full-matrix coverage by sharding the matrix across stages (build once, reuse artifact) rather than multiplying jobs; the nightly pipeline may use all 30; per-PR pipelines target ≤ 8. Quota protection: concurrency groups cancel superseded runs (`concurrency: group=branch, cancel-in-progress`).

## 22.2 Pipelines

| Pipeline | Trigger | Content |
|---|---|---|
| `pr.yml` | every PR | assemble debug + unit (JVM) + Robolectric + lint/token/manifest gates; ≤ 8 jobs |
| `instrumented.yml` | merge to main + nightly | emulator matrix smoke (API 26/33/35/36): editor smoke, IME fuzzer, a11y audit |
| `onedoc-apk-qa.yml` | release candidate / weekly / manual | the direct-APK QA (§24): build release → gates → install → drive → report PDF ≤ 30 jobs |

## 22.3 Publisher separation

Report/publish jobs (PDF assembly, release notes) run `if: always()` so evidence exists even for red runs — and the report's verdict banner reflects the QA shards, never the publisher's exit code. This separation is inherited from the predecessor program where a green publisher once masked real failures; it is codified here so it can never regress.

## 22.4 The cheap gates that catch the expensive mistakes

Manifest permission gate (exact set, §20.5) · deny-list dependency audit · token lint (DQ-1) · APK size gate · schema-freeze check (room schema JSON diff requires a D-nnn entry) · swear-jar check for banned APIs (main-thread IO in debug strictmode tests).

# Chapter 23 — Test environments

## 23.1 Emulator matrix

| AVD | API | Device class | Role |
|---|---|---|---|
| `od-api26` | 26 (Android 8.0) | Pixel 2, 2 GB | minimum-spec compatibility (C6) |
| `od-api33` | 33 | Pixel 4, 3 GB | Tier B baseline for budgets |
| `od-api35` | 35 | Pixel 6, 4 GB | Tier B+ / permissive UX checks |
| `od-api36` | 36 | Pixel 8, 8 GB | Tier A: full AI incl. LLM pack |

Host pins: platform `platforms;android-36`, build-tools `36.0.0`, command-line tools current stable; emulator images google_apis (no play store — deterministic). Tier emulation uses AVD RAM profiles; the LLM pack test runs only on `od-api36`.

## 23.2 What runs where

P0 catalogue cases run on all four; PERF on 33 (Tier B baseline); AI pack flows on 36 + 26 (graceful degradation proof); IME fuzzer on 26/33/35/36; a11y audit on 33/36. Known-allowed BLOCKEDs (from the predecessor's doctrine) are pre-registered in Appendix G with their environment fingerprints.

## 23.3 Determinism and hygiene

Emulators boot from fixed snapshots with cleared app data per run; clocks pinned for golden tests; locale en-US default, hi-IN run for the owner-locale set; screenshots captured at deterministic view states, embedded into the evidence PDF with run/case metadata stamped on the image corner.

# Chapter 24 — The direct-APK QA pipeline

## 24.1 Shape

`onedoc-apk-qa.yml`: (1) build signed release APK (provenance: commit, run id, SHA-256); (2) static gates (manifest, deny-list, size); (3) matrix jobs: install APK → grant nothing → run catalogue shards via instrumentation driving the real UI through `UiAutomation`/accessibility APIs; (4) per-case records PASS/FAIL/BLOCKED + screenshots + logs; (5) publisher job assembles `reports/onedoc-qa-<version>.pdf` with embedded screenshots and provenance; (6) defect-tracker diff job proposes new rows.

## 24.2 Evidence PDF (the owner's artifact)

Structure: cover (version, commit, run link, SHA-256) → verdict banner (counts by severity/verdict) → journey results with screenshot strips → per-case table (id, area, verdict, evidence link) → BLOCKED register → defect summary → methodology appendix. Every screenshot carries a corner stamp: build SHA + case id + timestamp. The PDF is committed to `reports/` and linked from the release.

## 24.3 Driving rules

Emulator driving uses the accessibility tree as the source of truth (resource ids are stable contract surfaces — `od_*` prefix); input synthesis accepts its own limits (§21.2). Flaky-once = rerun with same seed; flaky-twice = quarantine with defect id. Assertion failures include the accessibility snapshot dump — no "element not found" without the tree attached.

# Chapter 25 — Defect management

## 25.1 Flow

![Defect flow: found → triaged → fixed (test first) → verified on APK → closed.](figures/fig-defects.png)

Defects live in `reports/onedoc-defect-tracker.md` (append-only rows; the predecessor's tracker format and history are preserved untouched in the same directory). Every row: id (OD-001…), source case id, build SHA, severity, repro, evidence link, status, fix commit, verified-on run.

## 25.2 Severity

**S1** — data loss/corruption, crash, law violation, security; release blocker always. **S2** — wrong result, budget regression, broken P0 UX criterion. **S3** — polish, DQ design failures. Fix rule: a fix lands only with a test that failed first (regression test) — no test, no fix.

## 25.3 Triage categories

S-EDIT (engine), S-IME (input), S-IO (formats), S-AI (models/ladder), S-UI (design), S-PERF (budgets), S-A11Y, S-SEC (always S1), S-STATE (durability), S-CREW (scope creep — a feature nobody asked for; triaged by *removing* it, not fixing it, per §1.4).

## 24.4 Evidence-PDF schema (normative sections)

| # | Section | Required fields |
|---|---|---|
| 1 | Cover | app, version, versionCode, commit SHA, workflow run id+URL, APK SHA-256, date, catalogue version |
| 2 | Verdict banner | counts by verdict (PASS/FAIL/BLOCKED), by area; overall GO/NO-GO with rule citation (§21.2) |
| 3 | Journeys | J1–J5 step tables with per-step screenshot strips |
| 4 | Case results | full table: case id, area, level, AVD, verdict, evidence ref (screenshot/log), duration |
| 5 | Performance | budget table actuals (§21.4) with run links |
| 6 | BLOCKED register | each block: case, reason, environment fingerprint, first-seen, retries |
| 7 | Defect summary | new/open/closed since last report, tracker link |
| 8 | Method appendix | matrix description, driving rules, tool versions |

Layout rule: screenshots are embedded (not linked) at 2-up per row with corner stamps (§23.3); the PDF is self-contained — a printed copy proves as much as the run link.

## 24.5 Case-procedure format (how cases are written down)

Every catalogue case (Appendix C) expands in the QA harness to a procedure: `given / when / then` with exact app state, driver commands, and assertions. The harness sources procedures from `qa/onedoc/procedures/<case>.json` (generated skeleton at G3 from the catalogue; humans/agent refine assertions). A case without a procedure file cannot enter the run manifest — this is what stops "we tested it" claims that no one can replay.

## 25.4 Defect metrics (what the tracker reports)

Lead time to fix (median by severity), reopen rate (< 5%), BLOCKED aging (no block older than 2 cycles without a tooling-change decision), S1 count at any gate (must be 0 to pass), fix-with-test rate (100% by rule §25.2). Metrics come from tracker rows only — no side spreadsheets; the tracker is the single source (same discipline as the predecessor's tracker, which stays untouched for history).

## 24.6 Writing assertions that do not flake

Rules learned the hard way (predecessor cycles), applied to every procedure file:

1. **Assert on the accessibility tree, not pixels.** Text, content-desc, resource ids (`od_*`), and node states are deterministic; pixel colors are not (antialiasing, GPU quirks).
2. **Wait for states, never sleeps.** `waitUntil { nodeExists / propEquals }` with budgets; a `sleep` in a procedure is a defect in review.
3. **Pin the seed for anything random.** Content generators take seeds from the run manifest; failures replay byte-identical (§16.3).
4. **One logical assertion per wait cycle** — compound asserts report which conjunct failed (procedure format enforces assertion ids).
5. **Idempotent pre-conditions.** Procedures may assume: app installed, no prior data, permissions granted at feature use. They may not assume: time of day, locale beyond the run's pinned locale, battery level, network (there is none — assert its absence where relevant).
6. **Screenshots are evidence, not assertions** (except DQ visual checks, which diff against committed baselines with a 1% perceptual tolerance and human review on miss).

Flaky history is tracked per case in the run manifest; a case with 2 flakes in 30 days enters quarantine with a defect id (§24.3) — flakiness is a bug in the test or the app, never weather.

## 23.4 Device-farm notes (emulator tier fidelity)

AVD RAM profiles approximate real tiers but are optimistic on thermals and storage speed. Consequences: (1) LLM budgets measured on API 36 AVD carry a ×1.5 safety factor for physical Tier A devices before the capability is claimed in release notes; (2) thermal-descent tests (E_AI_THERMAL) are simulated via a test hook (diagnostics hidden toggle), never by cooking a core; (3) storage-full tests use a quota'd loopback path, not a filled disk. Where emulator truth is unknowable (cellular radios, real mics), the case is L5 and pre-BLOCKED (Appendix G doctrine) — honesty over theater.

## 23.5 Locale, timezone and layout runs

Nightly adds: hi-IN run (owner-locale strings + IME-03 fixtures), ar-RTL layout sweep (mirroring), timezone torture (clock jumps across save/snapshot boundaries — TC-STATE-006), font-scale 2.0 walk (DQ-5 evidence refresh). Tablet: 800dp/1280dp landscape sweep of home/editor/scan/settings (TC-ENV-003) — measure adaptation per §6.4(3), not stretched-phone layouts.

## 22.5 Quota math (how the matrix fits 30 jobs)

Full pipeline: 1 build+gates → 4 matrix QA shards (26/33/35/36) → 1 journeys shard → 1 perf shard → 1 security shard → 1 evidence publisher = 9 jobs (≤ 30 ✓) at ≤ 3 parallel by matrix-group scheduling (two waves). Nightly instrumented adds fuzzer×4 + a11y×2 + locale×2 = 8 jobs, reusing builds. PR pipeline: build+unit+lint+flavor-matrix = 6–8 jobs. The manifest publishes per-run job counts — budget breach is a visible number, not a vibe.

## 25.5 Defect row schema (tracker columns, exact)

`id | discovered (date, cycle) | source case | build SHA | severity (S1/S2/S3) | category (S-*) | title | repro (steps or procedure ref) | evidence (links) | status (open/in_progress/fixed_pending_verify/verified/closed/wontfix-owner) | fix commit | verified-on (run id, case) | notes`

Rules: rows append-only (status transitions edit the row in place with a dated note; never delete); `wontfix` requires owner sign-off (release note listing, §28.1); severity overrides are owner-only. The tracker renders to the release PDF via the same engine as the evidence report (one renderer, one style).

## 24.7 The qa-driver module (code layout)

```
qa-driver/src/main/
  pages/        # screen objects: Home, Editor, Sheets, Scan, Assistant, Settings (a11y-id based)
  steps/        # one object per catalogue case group, methods = procedure steps
  verdict/      # VerdictRecorder: PASS/FAIL/BLOCKED + evidence paths + timings
  drivers/      # uiautomator wrappers, gesture helpers with honest limits (§21.2)
  rules/        # budgets, wait policies, screenshot corner-stamper
  manifest/     # reads Appendix U table → run manifest (shards, seeds)
```

Rules: pages never assert; steps assert via verdict recorder only; drivers expose capability queries (`canHoldDrag()` false on emulator → procedure auto-marks BLOCKED with fingerprint, §21.2) — the harness cannot lie about what it clicked.

## 21.8 The G7 audit script (the final acceptance walk)

The gate-7 evidence is presented in this exact order, and the owner (or a reviewer) can replay it in ~45 minutes:

1. **Cover math (5 min):** catalogue version, case count, verdict counts — every number links to the manifest.
2. **Journeys (15 min):** five strips left-to-right; each step's assertion visible; artifacts open.
3. **Laws & properties (5 min):** LAW suite green + property suite seeds/run links.
4. **Performance & size (5 min):** budget table actuals; size gate log.
5. **Security (5 min):** SEC suite + manifest permission diff (empty) + network-silence probe log.
6. **BLOCKED register (5 min):** every entry has reason + retry history + owner-relevant consequence.
7. **Defects (5 min):** tracker diff; zero open S1/S2 asserted; S3 list previewed for release notes.

A gate report not structured this way does not close G7 — the audit script is the DoD's reading order.

## 23.6 The IME fuzzer farm schedule

Per PR touching `core-editor`: Robolectric fuzzer (scripts ×10k steps) in CI. Nightly: full farm on 4 AVDs × script set (gboard-en-sim, samsung-sim, hindi-translit-sim, generic-AP26) × 50k steps with randomized op interleaving; seeds rotate daily; a red seed pins a defect with its replay JSON. Recording new keyboards: run the record harness on an AVD with the target IME attached, commit the JSON script — the farm picks it up next night (§15.5). The farm's verdicts roll into the nightly report next to the catalogue shards; L5 evidence always cites the farm run id.

## 22.6 CI security and secrets

Runners get no secrets: the RC keystore is a base64 secret injected only into the release-build job, never printed; owner keystore arrives out-of-band (§N.5) and never enters CI at all. Third-party actions are pinned by commit SHA (allow-list in the workflow lint); no `pull_request_target` on forks (this repo is single-party; the rule stays for hygiene). Logs are the leak surface to police: no APK paths with tokens, no environment dumps (a lint scans workflow logs post-run in the publisher job). Emulator snapshots carry no user data (§23.3) — they are boot-state only, rebuilt weekly from the pinned images.

## 24.8 Case-triage runbook (when a shard goes red)

1. Read the assertion id + attached a11y dump (never guess from the title).
2. Reproduce locally with the same seed (`dev.sh qa <case>`); if it passes locally ×3, suspect the environment → rerun shard once; still red → environment defect (S-PERF class against harness) with the shard log.
3. Real red: minimality (which step first fails), then §25 flow — defect row same day.
4. BLOCKED-path check: was the driver honest (`canHoldDrag()` etc.)? If the red is actually a blocked gesture misfiring as FAIL, fix the driver capability query — a false FAIL is as bad as a false PASS (§21.2 doctrine cuts both ways).

## 24.9 Reading a QA log line (the format every case prints)

```
[TC-EDIT-IME-01] avd=od-api33 build=abc1234 seed=88410
  step 3/7 wait node od_edit_body ... ok (1.2s)
  step 4/7 ime glide-replace script gboard-en-sim ... ok
  step 5/7 assert single-op-undo ... FAIL
    expected: undo count == 1 after commit batch
    actual:   undo count == 3 (ops: insert,delete,insert)
    tree: <dump attached: fails/TC-EDIT-IME-01/tree-step5.json>
  VERDICT: FAIL (defect candidate) evidence: fails/TC-EDIT-IME-01/
```

Format rules: one line per step (action + duration), assertions quote expected vs actual (never "assertion failed" bare), evidence paths relative to the run artifact root. The publisher parses this format directly into the evidence PDF's case table — the log *is* the source of the report, never retyped.

## 21.9 The three-question release review (the owner's shortcut)

Before reading anything else in a release's evidence, three questions with one-line answers:

1. **Is it the real artifact?** SHA in provenance = SHA of the downloaded APK.
2. **Does it work for a human?** J1–J5 strips green (the journeys are the product).
3. **Is anything hidden?** BLOCKED register + defect diff + fidelity notes — read these three before believing the green.

If all three satisfy, the release is good; the remaining 190 pages of evidence exist for the day one of them doesn't.

## 24.10 The evidence-PDF build script

The publisher job renders the report from structured run output (`verdict/*.json` + `journeys/*/steps.json` + screenshots) through the same PDF engine as this blueprint — one renderer, one style, zero retyping. Inputs are checksummed into the report footer (run manifest hash), so the PDF itself is verifiable against the run that produced it. A failed publisher rerun must produce byte-identical output modulo timestamps (Law L6 applied to our own tooling).
