@PART: PART XI — BUILD, ACCEPTANCE AND DELIVERY
@PARTDESC: Gradle topology and flavors, the five acceptance journeys end-to-end, the release checklist, signing and the provenance bundle. This part is what "deliver the app" concretely means.

# Chapter 26 — Build topology

## 26.1 Gradle

Gradle wrapper (pinned distribution), version catalog, AGP and Kotlin pinned per Appendix F. Modules per §10.1. Build types: `debug` (strictmode, leak-canary-free — no telemetry ever, leak canary is local-only, allowed), `release` (R8 full, resource shrinking, no debuggables). Signing: debug keystore for QA; release keystore provided by the owner at the gate-8 step (until then, release builds are signed with a CI-held keystore whose key is marked "release candidate").

## 26.2 Flavors (C9 — reserved)

`full` (the studio, default) and `writer` (library+editor+templates+formats only; feature modules scan/assistant/search-semantic excluded by flavor-aware DI). v1.0 ships `full`; the `writer` flavor must keep assembling in CI so the seam never rots, but is not distributed unless the owner opts in (D-reserved).

## 26.3 Versioning

`versionName MAJOR.MINOR.PATCH`, `versionCode` monotonic; build stamps commit SHA + run id into `BuildConfig` and the About screen (F-089). Every artifact name embeds version+code+SHA: `OneDoc-v1.0.0-<code>-<sha7>.apk`.

## 26.4 Size budget

APK ≤ 25 MB without packs (§21.4): enforced by a CI gate that fails the build when the release APK exceeds the budget; per-PR size delta reported in the job summary. Fonts subset; PNG assets quantized; no unused ABI splits shipped (single universal APK for direct distribution; ABI splits only if the owner requests them).

# Chapter 27 — Acceptance journeys (J1 … J5, full scripts)

## 27.1 J1 — Blank page to formatted letter to PDF

Start: fresh install, no docs. Steps: launch (T0) → tap FAB → type salutation → select line → bold via toolbar → H1 the subject line → insert divider → type two paragraphs → menu → Export PDF → save via SAF → open PDF from files. Assert: ≤ 2 taps to editor (UX-02), formatting visible, PDF pages with correct measure, word count ±1% (UX-49), total median time under 3 min on API 33. Evidence: screenshot strip + the exported PDF attached. Case: TC-J1.

## 27.2 J2 — Photograph three pages into one document

Start: home. Steps: FAB → Insert → Scan → capture 3 pages (fixture images via emulator camera virtual scene) → reorder page 2 before page 1 → OCR → review screen shows low-confidence word marked → fix one word → insert. Assert: editable paragraphs in chosen order, confidence marks, images attached as assets, conversion note present, ≤ 60 s/page on API 33 (UX-09). Case: TC-J2 (OCR pack present) and TC-J2-degraded (no pack → ends at save-image with reason, ladder rung 6 UX).

## 27.3 J3 — Dictate minutes, tidy, share as DOCX

Steps: new doc → dictate fixture audio (emulator mic injection) → partials appear ≤ 1.5 s (UX-10) → stop → preview card labeled with method → insert → select first line → H1 → Summarize (extractive rung on API 33) → preview card labels method (UX-47) → insert below → Export DOCX → share via share sheet. Assert: docx opens in importer round-trip with headings/list parity (F2), all inserts are single-undo groups (UX-06). Case: TC-J3 (+ TC-J3-llm variant on API 36 with gemma rung labeled).

## 27.4 J4 — Find the paragraph about the warranty in 20 documents

Setup: seed corpus (20 docs incl. a 6-page "Appliance manual" mentioning warranty once obliquely). Steps: home search "warranty" → FTS results with snippets ≤ 300 ms (UX-08) → tap hit → editor opens at block with highlight (N5). Variant with `embed-minilm` pack: query "what covers repairs" surfaces the warranty paragraph under "related". Case: TC-J4 / TC-J4-semantic.

## 27.5 J5 — Recover half a deleted document

Steps: open seeded 3,000-word doc → select from mid-document to end → delete → type replacement sentence → wait 1 s → `adb shell am kill` → relaunch → assert full content minus zero words present (journal replay) → now Versions → open auto snapshot from before deletion → preview → Restore → assert pre_edit snapshot created, deletion undone, redo stack cleared. Assert: zero loss (UX-11), restore ≤ 30 s (UX-07). Case: TC-J5 (the UX-11 kill trial is TC-STATE-005's 100-trial version).

# Chapter 28 — Delivery

## 28.1 Release checklist (G8)

1. G7 evidence green on the RC build (same SHA as release).
2. Defect tracker: no open S1/S2; S3 list accepted in release notes.
3. Journeys J1–J5 green on matrix; evidence PDF assembled and committed.
4. Manifest/deny-list/size gates green on the exact release artifact.
5. Artifacts: universal release APK (+ AAB optional), SHA-256, `.odpack` bundles documented (never shipped inside APK).
6. Release notes: features, fidelity notes, known BLOCKEDs with reasons, defect summary — no marketing language, no "known issues" framing of S1/S2 (they cannot exist at G8).
7. Tag `v<X.Y.Z>`; provenance bundle committed (§28.2).

## 28.2 The provenance bundle

`releases/<version>/provenance.json`: version, versionCode, commit SHA, workflow run id+URL, APK SHA-256 + size, pack manifest hashes referenced (not embedded), catalogue version (case count + commit of qa CSV), tool versions (Appendix F). The owner verifies by recomputing the APK hash — trust is a checksum away, as promised in P5/C10.

## 28.3 Post-release

Crash-free operation is *expected, not monitored* — there is no telemetry (C3). The owner's feedback loop is the diagnostics screen export (a local text file the owner can share manually if they choose) and the defect tracker. Version upgrades follow the same gate discipline with migration tests (§11.4) as the entry gate.

## 26.5 CI caching and speed hygiene

Gradle build cache + configuration cache on; wrapper distribution cached at runner level; emulator AVDs pre-booted from golden snapshots (§23.1) with app data cleared per run; artifact reuse: one release build fans out to all QA shards (no shard rebuilds). Budget: per-PR pipeline ≤ 12 min P95; nightly full matrix ≤ 75 min. Cache poisoning guards: caches keyed by lockfile hash; no cache writes from release branches' QA runs.

## 28.4 Owner handoff note (template, committed with the release)

```
OneDoc v<X.Y.Z> — handoff
What shipped: <features by area, 10 lines max>
Quality: <catalogue verdicts; journeys; budgets; BLOCKED register summary>
Known limits: <S3 list + fidelity notes worth remembering>
Artifacts: APK + SHA-256, evidence PDF, provenance.json, tracker link
How to verify in 5 minutes: install -> J1 walkthrough -> About self-test -> compare SHA
```

The note is deliberately owner-shaped: verification-first, jargon-light, and honest about limits — the same voice as §28.1's release notes rule.

## 27.6 Journey evidence layout (how J-cases document themselves)

Each journey produces a self-contained folder: `artifacts/journeys/<J-id>/` containing `steps.json` (step, action, assertion, verdict, duration) and `screens/NN-<step>.png` (corner-stamped). The evidence PDF renders journeys as a strip per step with the assertion text as caption — the owner walks the story left-to-right without reading logs. Journey steps double as the demo scripts (Appendix S) — one source, two uses, no drift.

## 28.5 Owner verification runbook (5 minutes, offline)

1. Download APK + `provenance.json` from the release.
2. `sha256sum OneDoc-…apk` — compare to provenance (match = artifact integrity).
3. Install; launch; run About → self-test (≤ 20 s, must pass).
4. Walk J1 (create → format → export PDF) — the letter lands in your files.
5. Optional deep check: `apkanalyzer manifest permissions <apk>` shows the §20.5 set exactly.

If any step fails, the release is not accepted — file the tracker id from the evidence PDF and stop. Trust arrives from checksums and tests, never from promises (P5, C10).

## 28.6 Release-day script (automated, idempotent)

1. `./scripts/release-verify.sh v<X.Y.Z>`: checks tag → build from tag → SHA match to provenance → static gates.
2. Re-run TC-J1..J5 + SEC-P-03 on the tag build (30-minute smoke; full matrix already done at G7 — the smoke proves *this* artifact).
3. `gh release create v<X.Y.Z>` with APK, evidence PDF, provenance.json, notes (Appendix M voice).
4. Post-release task graph update: gate G8 → closed; maintenance mode §30.4 armed (nightlies continue).
5. Rollback posture: a bad release is never "patched" — a new version ships through the same gates; the bad tag's release notes get an amber supersede line.

## 26.7 The local build and run script (dev loop)

```bash
./scripts/dev.sh build    # assembleFullDebug + install on first booted AVD
./scripts/dev.sh qa TC-J1 # build RC, install, run one journey, open screenshots
./scripts/dev.sh laws     # JVM law+property suite only (fast inner loop)
./scripts/dev.sh clean    # uninstall + clear data + reboot AVD state
```

The scripts are thin wrappers over the N.4 commands — same paths, same gates, so "works on my machine" and "works in CI" are the same sentence. CI invokes the identical scripts (workflow lint asserts it), keeping drift between local and CI at zero.
