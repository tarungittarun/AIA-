# Chapter 27 — Traceability matrix

## 27.1 Mechanism

`tools/traceability.py` scans three sources and emits `reports/traceability.csv`:

1. This blueprint (F/UX/TC/§ ids by regex).
2. Source headers and commits (`Refs:` trailers).
3. Test results JSON (latest full-lane run).

Invariants enforced (CI `traceability` check):

- Every F-xxx has ≥ 1 TC and ≥ 1 commit.
- Every TC has ≥ 1 F/UX binding and a latest status.
- Every § cited in code exists in the blueprint.
- No TC references a nonexistent F (and vice versa).
- P0 features cannot hold status `not-implemented` at G7.

## 27.3 Traceability script outline (tools/traceability.py)


# Chapter 28 — Observability and diagnostics (local-only)

## 28.1 Principles

Observe without transmitting: all telemetry-equivalents are local, scrubbed, size-capped, user-visible, and user-exportable. If a data point cannot be shown to the user in Diagnostics, it is not collected.

## 28.2 What is recorded (the local ring)

| Signal | Where | Retention |
|---|---|---|
| Crash/uncaught-exception records (stack, thread, recent breadcrumbs) | `logs/crash/` | 5 latest |
| ANR watches (main-thread block > 5 s during user action) | ring | 7 days |
| AI job records (capability, pack, duration, memory, fallback rung used, cancel source) | ring + per-note provenance | 7 days |
| Repository timings p50/p95 (per operation class) | ring (aggregates only) | 7 days |
| Feature usage counters (module opens, actions) — coarse, per-install | DataStore | until cleared |
| Alarm scheduler outcomes | ring | 7 days |

`adb logcat` during a QA run is captured by the harness (§22.5) — the app itself never streams anywhere.

## 28.3 Scrubbing rules

Ring scrubber reduces absolute paths to basenames, strips phone-number/email patterns (regex), keeps calculator expressions verbatim (product content), and replaces account names (`never present anyway`). The share preview shows the exact final text (F-081). Unit tests pin scrubber behavior (TC-SEC-scrub).

## 28.4 Self-test and health computation

§17.8 defines the script; health cards derive from the same primitives (storage %, quick_check, pack hashes, alarm capability). Self-test is synchronous (≤ 10 s) with per-step progress; results are artifacts (`diagnostics/selftest-<ts>.json`), one tap to share.

## 28.5 Diagnostics ring schema (normative)

```sql
CREATE TABLE diag_ring (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts INTEGER NOT NULL,            -- epoch millis
  kind TEXT NOT NULL,             -- crash|anr|ai|repo|alarm|feature
  severity TEXT NOT NULL,         -- info|warn|error
  module TEXT NOT NULL,
  message TEXT NOT NULL,          -- scrubbed
  detailJson TEXT                 -- structured extras (timings, rung, ids)
);
CREATE INDEX idx_diag_ring_ts ON diag_ring(ts DESC);
```

Retention sweep: on startup keep `severity=error` rows 7 days, `info/warn` 3 days, hard cap 2 MB (oldest evicted first). Export = JSON Lines, previewed verbatim before sharing (F-081). Feature counters live in DataStore under `stats.*` keys, viewable in Diagnostics → Usage (module opens, actions per module) — coarse, local, clearable.


# Chapter 29 — Maintenance and update policy

## 29.1 Code health practices

No orphan code: detekt + unused-module scan per gate; dependency refresh window quarterly (post-G7) with ledger entries; blueprint drift check at each minor release (§ refs validated); the task graph closes at G8 and a v1.1 graph seeds from the defect ledger + P2 backlog.

## 29.2 Data evolution

Room migrations only forward; every migration gets a fixture test (§21.3 backups as inputs); FTS rebuild command for catastrophic index cases; `indexes/vectors.bin` versioned with a rebuild path; backup format versioned — older-app-rejects-newer-backup with a clear message (STATE case).

## 29.3 Model pack evolution

Packs version independently of the app; `catalog.csv` records supported pack versions per app version; a pack too new is rejected with "update the app" guidance; a pack too old runs with an eval-waiver note in Diagnostics. Eval kit (§16.8) re-runs per accepted pack version — results versioned in-repo.

## 29.4 Documentation maintenance

This blueprint is versioned with the code; every merged feature PR must land its spec delta in the same merge (docs-drift check §24.4); the changelog accumulates in `RELEASE-NOTES.md`; the defect ledger is never pruned (history is evidence — the owner's standing practice).

## 29.5 Model/pack update decision tree (operational)

```
New pack version published by owner
├─ Eval kit green (§16.8 thresholds)
│   ├─ App catalog.csv supports it → mark supported; note in ledger; users import at will
│   └─ App catalog too old → app update release adding catalog row (minor bump)
└─ Eval red → do not distribute; record eval JSON; fix or pin previous version
App update with behavior-affecting prompts (§16.12)
└─ Eval re-run mandatory before merge (docs-drift check enforces version bump)
```

## 29.6 Deprecation policy (in-app)

Removed settings keys migrate once with documented defaults (registry version row); removed features surface a one-line "moved/removed" card in Diagnostics → Changelog for one minor release. Nothing silently disappears — small product, high trust.

## 29.7 Changelog discipline example (RELEASE-NOTES entry quality)

```
### Fixes
- Calculator: `5 + =` now yields 10 (pending-operator repeat, Google parity). [D-014]
- Recorder: pauses cleanly on incoming calls; file kept to the pause point. [D-021]

### Honest register
- Blocked during QA: stationary hold-then-drag selection needs a physical device
  (emulator input API limitation). Reported as BLOCKED, not failed.
- Known limitation: ICS import supports the documented RRULE subset; exotic rules
  import as one-off events with a note.
```

Every bullet carries a ledger id and the honest register is never empty — if nothing is blocked, the line says "None this release" (the absence is the claim).

# Chapter 32 — Final acceptance and sign-off (G7 script)

The owner-facing acceptance walk, in order, each step against real artifacts:

1. **Identity**: install `myspace-one` release APK on a device/emulator → About shows version + commit + APK SHA-256 matching the release bundle.
2. **Privacy proof**: manifest shows zero internet-class permissions (S2); airplane mode on; full smoke (J-05) passes.
3. **Calculator**: run Catalogue-0 CALC set (or read the L5 PDF of record); spot-check TC-ONE-C-004 (`5+ =` → `10`), C-008 (`1÷3×3` → `1`), C-023 (theme diff) by hand.
4. **Flavor**: install `mycalc` APK → zero permissions (F-038), parity spot-check, no module remnants.
5. **Modules**: one journey each (J-01…J-10) or gate-report review with artifact paths.
6. **AI**: with packs → OCR a fixture, transcribe a fixture, summarize a note; without packs → the same features degrade exactly per §16.7; pack manager rejects the tampered fixture pack.
7. **Data**: backup → wipe → restore (J-03); migration fixture log reviewed.
8. **A11y/UX**: UX-001…UX-020 checklist review with screenshots.
9. **Evidence**: traceability matrix shows all P0 green; defect ledger has no open S1/S2; blocked register reviewed and accepted.
10. **Sign-off**: owner accepts (or files defects); G7 report marked ACCEPTED with date; release published per §25.5.

## 32.2 The G7 walkthrough, narrated

The owner starts with identity (step 1) because every later proof depends on "is this the build I think it is": the About screen SHA must equal the release-notes SHA must equal the CI artifact SHA — three independent views of one truth. Privacy (step 2) is proven, not promised: airplane mode is toggled by hand and the manifest is read on-device. Calculator (step 3) is the emotional core — the owner replays the exact behaviors their old guides named, including the two historical bugs (`5+ =`, `0.999…`), now expected dead. The flavor (step 4) proves the product story ("a calculator, nothing else") in one permission screen. Modules (step 5) ride the journey evidence; the owner may re-run any single journey by hand in minutes. AI (step 6) shows the ladder honestly: capabilities on, capabilities off, same features usable. Data (step 7) is the trust moment: backup, wipe, restore, identical counts. A11y/UX (step 8) rides screenshots plus one TalkBack pass. Evidence (step 9) is where the program's honesty is auditable: traceability green, ledger closed, blocked register — if any — owned and accepted. Step 10 is a date and a signature. If any step surprises the owner, the release stops; surprise is a defect of the process, not of the owner.

## 32.3 Common acceptance questions (owner asks / spec answers)

**"Prove it's not phoning home."** Manifest has no INTERNET permission (S2 artifact); dex scan shows no socket classes (SC-03); airplane-mode journey J-05 green on the exact APK; the app cannot — structurally — transmit.

**"Why should I trust the green report?"** The report builder reads only manifest-verified artifacts; every case row carries screenshots and timings; the harness code is in-repo and re-runnable against any APK by hand (§22.13).

**"What if a gesture wasn't tested fairly?"** The blocked register names it, the prevention, and the unblock path; BLOCKED never counts as pass (§15.6) — and physical-device runs use the same harness (§21.8).

**"How do I know updates won't break my data?"** Migration fixtures run old backups/schemas through new code (STATE-mig), install-over is itself a tested case (TC-SEC-upgrade), and backups restore transactionally or not at all (J-03).

**"Where do the AI models come from?"** You install packs yourself from files with published SHAs; the app verifies hashes at import *and* at load; it never downloads anything (C5, §16.8).

**"What's my escape hatch?"** Export everything (§26.3), unencrypted option; notes export as Markdown; playlists as M3U; events as ICS — your data leaves in open formats, on your terms.
